# CORTEX — Ask your documents

<img width="1470" height="816" alt="image" src="https://github.com/user-attachments/assets/57586112-8ec4-4079-b3b4-a0382a2ffce3" />


A **Retrieval-Augmented Generation (RAG)** web app built with Ruby on Rails.
Upload any document (PDF, Word, HTML, Markdown, CSV, JSON, plain text) and ask
questions about it in natural language. Answers are generated by the LLM
provider *you* choose — OpenAI, Anthropic, Google Gemini, or a fully local
Ollama — and are grounded only in what your documents actually say.

```
   ┌─────────────┐   upload    ┌──────────────────────────────────────────┐
   │   Browser   │ ──────────► │  DocumentsController                     │
   │ (chat + UI) │             └──────────────┬───────────────────────────┘
   └──────┬──────┘                            │ IndexDocumentJob (background)
          │ SSE stream                        ▼
          │                      ┌──────────────────────────────────────────┐
          ▼                      │ extract → chunk → embed → store          │
   ┌──────────────┐              │  DocumentExtractor  Chunker              │
   │ RagService   │              │  EmbeddingService (any provider)         │
   │ (RAG query)  │              └──────────────────┬───────────────────────┘
   └──────┬───────┘                                 │ vectors
          │                                  ┌──────▼──────┐
          │            question embedding     │ PostgreSQL │
          │──────────────────────────────────►│ + pgvector │
          │            nearest chunks ◄───────│ (3072-dim) │
          ▼                                  └─────────────┘
   ┌──────────────┐
   │ LLM adapter  │  OpenAI / Anthropic / Gemini / Ollama
   │ (streaming)  │  "answer using ONLY this context"
   └──────────────┘
```

## Architecture in one minute

1. **Ingestion** (`IndexDocumentJob`)
   Upload a file → `DocumentExtractor` pulls out plain text (pdf-reader, docx
   gem, Nokogiri…) → `Chunker` splits it into overlapping ~1,500-char chunks →
   `EmbeddingService` converts each chunk into a vector via the configured
   embedding model → vectors are stored next to the text in the `chunks` table.

2. **Query** (`RagService`)
   Your question is embedded with the **same** model → pgvector finds the 6
   nearest chunks by cosine similarity → those chunks become the *context* in
   a system prompt → the active chat provider streams its answer back to the
   browser over **Server-Sent Events**.

3. **Providers** (`Llm` registry + `app/services/llm/*`)
   Every provider (OpenAI, Anthropic, Gemini, Ollama) is a small adapter class
   with the same two methods: `chat(messages, stream:)` and `embed(text)`.
   The admin panel switches the *active* provider, stores API keys encrypted
   (ActiveRecord encryption), and can test each connection live.

## Setup

### Prerequisites

- Ruby 3.3+
- Rails 8.1+
- PostgreSQL 16 (Homebrew: `brew install postgresql@16`)
- pgvector extension for **your** PostgreSQL version

### 1. Install pgvector

```sh
# Homebrew pgvector may be built for a newer PG than yours. Check:
ls /opt/homebrew/opt/pgvector/share/postgresql*/extension/vector.control 2>/dev/null

# If there's no directory matching your PG version, compile from source:
git clone --depth 1 --branch v0.8.0 https://github.com/pgvector/pgvector /tmp/pgvector
cd /tmp/pgvector
make PG_CONFIG=/opt/homebrew/opt/postgresql@16/bin/pg_config
make install PG_CONFIG=/opt/homebrew/opt/postgresql@16/bin/pg_config
```

> On macOS the make step can fail with `stdio.h not found` because PostgreSQL
> was built against a different SDK. Fix: pass
> `PG_SYSROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX15.1.sdk` (use an
> SDK that actually exists: `ls /Library/Developer/CommandLineTools/SDKs/`).

### 2. Create the app's database

```sh
rails db:create db:migrate db:seed
```

The `enable_extension "vector"` migration does the rest. The seed creates the
four providers (OpenAI, Anthropic, Gemini, Ollama) with sensible default
models and **no API keys**, plus two demo users:

| Email                | Password     | Role  |
| -------------------- | ------------ | ----- |
| `admin@cortex.dev`   | `password123`| admin |
| `user@cortex.dev`    | `password123`| user  |

### 3. Add API keys & activate a provider

1. Start the server: `bin/rails server`
2. Open `http://localhost:3000/admin/providers`
3. Click **Configure** on a provider → paste your API key → save
4. Click **Make active** on one provider, and **Test connection** to verify

No key needed for Ollama:
```sh
brew install ollama && ollama serve   # in one terminal
ollama pull llama3.2                  # chat model
ollama pull nomic-embed-text          # embedding model
```

> **Embeddings note:** Anthropic has no embeddings API, so leave its
> *embedding model* blank — the app automatically uses another enabled
> provider for embeddings (any provider with an embedding model set).

### 4. Upload & chat

1. Sign in as the admin demo user (`admin@cortex.dev` / `password123`)
2. Open `http://localhost:3000/documents` — drag & drop any PDF/DOCX/HTML/MD/TXT/CSV/JSON
3. When the card shows **completed**, open `http://localhost:3000/queries` and ask away
4. Answers stream in live, with **source chips** showing which chunks were retrieved and how relevant they were
5. Chat history is per-user and persists across visits; **Clear chat** wipes it

## Authentication & roles

Cortex uses Rails 8's built-in authentication (the `rails generate
authentication` generator): a `user` model with `has_secure_password`, a
cookie-based `session` model, and the `Authentication` concern providing
`current_user` / `authenticated?`. On top of that sits a tiny **role system** —
a `role` column on `users` (`user` or `admin`):

| Action                                   | Guest | User | Admin |
| ---------------------------------------- | :---: | :--: | :---: |
| Landing page, sign in, create account    |  ✅   |  ✅  |  ✅   |
| Chat (ask questions, own history)        |  ✖️   |  ✅  |  ✅   |
| Clear own chat history                   |  ✖️   |  ✅  |  ✅   |
| `/dashboard` (stats & activity)          |  ✖️   |  ✖️  |  ✅   |
| Documents (upload / manage / reindex)    |  ✖️   |  ✖️  |  ✅   |
| AI Providers (keys, activate, test)      |  ✖️   |  ✖️  |  ✅   |
| Users page (assign roles)                |  ✖️   |  ✖️  |  ✅   |

Notes:
- `QueriesController` scopes everything to `current_user` — you only ever see
  your own questions, answers, and sources.
- Admins cannot change their own role (no accidental self-demotion).
- Sign-up is open to anyone; new accounts start as plain `user`s.

## The clever bits (and why they're built this way)

### 1. One `vector(3072)` column for every embedding model

Different providers output different dimensions: OpenAI 1536/3072, Gemini
3072, Ollama 768/1024. PostgreSQL vector columns have a fixed dimension, so
Cortex:

1. **normalizes** every vector to unit length, then
2. **zero-pads** it to exactly 3072.

Cosine similarity between two zero-padded unit vectors is **identical** to the
original vectors' cosine similarity (they stay unit length, so cosine = dot
product). This means you can switch embedding models any time without
re-indexing — see `EmbeddingService.normalize_and_pad`.

### 2. Provider adapter pattern

`Llm` is a tiny registry mapping `Provider.slug` → adapter class
(`Llm::OpenaiClient`, `Llm::AnthropicClient`, `Llm::GeminiClient`,
`Llm::OllamaClient`). All expose the same interface, so `RagService` never
knows which provider it's talking to. **Adding a provider = write one adapter
class + one registry line.**

### 3. SSE streaming without a websocket

`QueriesController#stream` uses `ActionController::Live` to push
`data: {"type":"delta","payload":"..."}` frames. The Stimulus `chat_controller`
reads the response with `fetch` + `ReadableStream` and appends deltas to the
bubble with a blinking caret. No ActionCable, no background worker — just an
open HTTP connection.

The adapters yield each token the moment it arrives: the LLM clients
(`GeminiClient`, `OllamaClient`) feed raw HTTP fragments into a line buffer
that fires a callback per complete SSE/JSONL line, so the browser sees the
answer grow *while* the model is still generating — not in one blob at the
end. Error responses (429 quota, retired models, …) are also surfaced live
with the API's own message.

### 4. Chunking with overlap

A question's answer often spans a chunk boundary. `Chunker` carries 200
characters of context into the next chunk and only searches for sentence
breaks in the *new* portion (searching the overlap would re-find the previous
break and shrink chunks into nothing — a real bug we hit and fixed).

### The RAG prompt in one glance (`rag_service.rb`)

```
[Source 1] (from "quarterly-report.pdf", relevance 92.3%)
<retrieved chunk text>
---
[Source 2] ...
=== END CONTEXT ===

User question: What was Q3 revenue?
```

The system prompt instructs the LLM to answer *only* from that context, to say
"not in the documents" when it can't, and to cite `[Source n]` — which is why
the source chips under each answer are trustworthy.

## FAQ / troubleshooting

- **`extension "vector" is not available`** — pgvector isn't installed for the
  PostgreSQL version you're running (see step 1 above).
- **`undefined method 'vector'` in migrations** — the `neighbor` gem provides
  Rails integration for pgvector; make sure it's in your Gemfile (`bundle`).
- **401 / 403 from the API** — wrong or missing key in the provider config, or
  the model name doesn't exist for your account. Use **Test connection**.
- **`API error (429)` in chat** — rate limit / quota exceeded (e.g. Gemini's
  free tier caps at 20 requests/minute). Wait a minute and retry; the message
  includes the API's own "retry in Xs" hint when available.
- **`API error (404)` in chat** — the configured model was retired. Google's
  old `gemini-2.0-flash` / `text-embedding-004` are gone; use
  `gemini-3.5-flash-lite` or `gemini-3.6-flash` (chat) and
  `gemini-embedding-001` (embedding).
- **Query fails with "No active chat provider"** — activate one in
  `/admin/providers`.
- **Answers ignore my document** — confirm the document card says
  *completed* (the status badge auto-refreshes), and that the embedding
  provider you're using is enabled.
- **Uploads process slowly** — each chunk is embedded individually against the
  API; batched `embed_many` exists for OpenAI/Ollama. Realistically fine for
  personal document sets.
- **API keys in source control?** — No. Keys live encrypted in the `providers`
  table (ActiveRecord encryption, keys in `config/credentials.yml.enc`).
  Seeding also reads `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY`
  env vars if you prefer.

## Ideas to take it further (great learning projects)

- **HNSW index**: when your chunk count grows past ~100k, `add_index :chunks,
  :embedding, using: :hnsw, opclass: :vector_cosine_ops` (note: pgvector caps
  indexed dims at 2000 — you'd drop the padding to ≤2000)
- **Multi-turn chat**: keep conversation history in `queries` and feed it back
  to the LLM
- **Hybrid search**: combine vector similarity with PostgreSQL full-text
  (`tsvector`) for exact-keyword matches
- **New file formats**: e.g. `.xlsx` via the `roo` gem — one new branch in
  `DocumentExtractor`
- **Streaming providers**: swap SSE for a WebSocket if you want chat history
  persistence without page reloads
